# Sync Verification

The before-and-after integrity check I run around every data move between the Raspberry Pi 5 (capture device), the Mac (git/photo-pull workstation), the NVIDIA PC (training), and Jetson Orin Nano. Data quality is not only about correct labels — a batch that got half-copied or clipped by a bad sync flag is a quality failure too, so no copy is "done" until source and destination counts match and no label lost its image.

## Preconditions

- The copy has been scoped correctly (a named `media/photos/YYYY_MM_DD_run_N/` folder or specific checkpoint), ran without `--delete` on any reverse pull, and I have the source folder still available to count against.
- I know the expected count from the source filesystem and label file. The removed `PRUN`/`PALL` dashboard pages are not a source of truth; count the named run folder directly before and after transfer.

## Steps

1. **Count the source before the sync.**

   ```bash
   find /home/rsabavat/rc_car_code/media/photos/2026_07_02_run_1 -type f | wc -l
   ```

2. **Run the scoped, additive copy** (see `mac-to-pc.md` / `pc-to-mac.md`). Always dry-run with `-avn` first.

3. **Count the destination after** with the identical `find | wc -l`, and diff the two numbers. They must be equal. A short destination means a partial copy.

4. **Prove no label lost its image.** A JPG carries its steering label; a run folder created by `create_photo_run_dir()` is only removed by `cleanup_photo_run_dir()` when empty, so an incomplete run is a real folder of real files that can still be short. Run the trainer scan on the destination (see `data-governance/data-quality/image-quality-checks.md`) and confirm it reports `missing=0` — no label pointing at an image that never arrived.

## Stop condition

- Counts do not match, or the trainer scan reports any `missing` / `skipped_missing` rows. Do not train on or publish a batch that failed verification.
- The dry run showed a `deleting` line (stop and see `runbooks/sync-day/delete-risk.md`).

## Recovery

- **Destination short.** Re-pull only the affected run folder with `rsync -a` and no `--delete`. Never reverse-sync the whole tree to "fix" a count.
- **Labels missing images.** The image copy was incomplete — re-run the scoped copy of that run folder and re-verify. Do not delete the labels to make the scan pass.

## Cleanup

- No artifacts are generated by verification itself. If verification created a scratch count file, remove only that file. Never delete photos, logs, or checkpoints as part of "cleanup."

## Notes / history

- Recorded failure mode: a truncated batch is indistinguishable from a small batch until the trainer scans it and reports a low `used` count or a wall of `skipped_missing` rows. This check is what catches it before it silently poisons a training run.
- Good example on record: `rsync -a` (no `--delete`) of just one run folder, then a file-count diff confirming source and destination match.

## Evidence to attach

- Source and destination file counts, before and after
- The trainer scan `missing=` line proving no labels lost their images
- The exact rsync command run (direction, scope, flags)
- Run note and the run/model version involved
